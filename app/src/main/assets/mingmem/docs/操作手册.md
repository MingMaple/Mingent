# mingmem 操作手册

> 本文件**只给人（和接任的会话）读**。库内代码对它零引用，删掉内核照跑（洁净内核原则）。
> 分工：`README.md` 讲怎么接进别的项目；`docs/设计文档.md` 讲为什么这么设计；本文件讲**怎么用**。
> 所有样例都是 2026-10-26 23:1x 真跑出来的（Python 3.13.15 / SQLite 3.50.4 / Windows），不是手写示意。

---

## 0. 约定

| 写法 | 含义 |
|---|---|
| `mingmem <子命令>` | 已 `pip install -e .`（或装了入口）时的调用 |
| `python -X utf8 -m mingmem <子命令>` | 走 `PYTHONPATH` 的调用，**与上一种等价** |
| 退出码 0 / 1 / 2 | 成功 / 体检发现问题 / 用法或前置条件错误（明细见 `异常与附录.md`） |

**Windows 必须带 `-X utf8` 或设 `PYTHONUTF8=1`**，否则中文输出、`selftest` 会因默认代码页出错。

本手册默认已执行过一次 `init`。若没执行过，任何命令都会以退出码 2 停住并打印修复命令 —— 这是设计，不是故障（见第 2 节）。

## 1. 五分钟上手

### 1.1 前置

- Python ≥ 3.10（`pyproject.toml` 的 `requires-python`）。
- 纯标准库，无第三方依赖；SQLite 必须带 **FTS5**（官方 Python 自带的都有，`doctor` 会报「FTS5：可用」）。
- 向量通道是可选件，未安装 `sentence-transformers` 时自动降级为 BM25 + 图扩散，**不影响任何命令**。

### 1.2 初始化数据根（只做一次）

```
$ mingmem init --data-root D:\MemoryData --default-ns project:myproject
已初始化 mingmem
- 数据根：D:\MemoryData（已建 events/）
- 配置文件：C:\Users\<你>\AppData\Roaming\mingmem\config.json
- 默认命名空间：project:myproject
- 下一步：mingmem doctor ｜ mingmem add --text "第一条记忆"
```

之后所有命令都不用再带 `--data-root`。重复 `init` 会被拒绝（退出码 2），要换根请加 `--force`。

### 1.3 写一条

```
$ mingmem add --kind episode --text "今天把投影重建了一遍，确认事件流是唯一真相源。" --tags 架构,事件流
已写入 epis-261026231324-bb13 ｜ project:myproject ｜ episode ｜ 今天把投影重建了一遍，确认事件流是唯一真…
```

第一段是 id（`<kind 前 4 字>-<时间戳>-<4 位十六进制>`），后面所有按 id 操作的命令都用它。

### 1.4 查回来

```
$ mingmem recall --query "记忆内核 真相源 投影" --limit 5
```

输出是**六段式 briefing**（不是命中的片段堆砌）：

```
① 主题与范围：查询「记忆内核 真相源 投影」｜ 范围：project:demo、global｜ 命中 3 条｜ 时间跨度 10-26 23:13 ~ 10-26 23:13
② 时间线：
   - 10-26 23:13 [episode] 今天把记忆内核的投影重建了一遍，确认事件流是唯一真相源。（epis-...-3e3a）
   - 10-26 23:13 [episode] 引用事件流那条的后续：给投影加了 doctor 对账。（epis-...-f2dd）  ← 关联 epis-...-3e3a
③ 现状：
   （无已巩固的结论；可用 cycle + consolidate 生成）
④ 相关实体：
   #事件流(2)｜ #架构(2)｜ SQLite(2)｜ mingmem(2)
⑤ 情绪与偏好线索：
   （无）
⑥ 来源（为什么召回它）：
   - epis-...-3e3a ｜ project:demo ｜ 10-26 23:13 ｜ bm25#1(4.730) ｜ 分 0.830
```

**注意：`recall` 默认会写一条 `access` 事件**（访问强化：`storage += 0.05×(1-storage)`、`retrieval` 重置为 1.0、同批命中之间加共检索边）。
只读检索请加 `--dry-run`（不写 access 事件）。

### 1.5 体检

```
$ mingmem doctor
...
- 事件↔投影对账：一致（节点 10）
- 结论：通过
```

`doctor` 只读，退出码 0 = 通过、1 = 发现问题、2 = 没有配置数据根。

## 2. 三个位置：代码 / 配置 / 数据

| 位置 | 内容 | 会不会被别人覆盖 |
|---|---|---|
| **代码仓根** `.../记忆内核库/mingmem/` | 包、评测集、文档 | 升级代码只动这里 |
| **用户级配置**（Windows `%APPDATA%\mingmem\config.json`；POSIX `$XDG_CONFIG_HOME/mingmem/config.json` 或 `~/.config/mingmem/config.json`） | `data_root` 与可选 `default_ns` | 只被 `init --force` 覆盖；可用 `MINGMEM_CONFIG` 指向别的文件 |
| **数据根**（`init` 指定的目录） | `events/*.jsonl`（**唯一真相源**）、`index.sqlite`（可重建投影）、`.mingmem-lock`（运行期锁目录） | 只有 `add/recall/cycle/consolidate/correct/forget/restore/purge` 会写；`index.sqlite` 删了会自动重建 |

**没有配置就不工作**（退出码 2）。这是 D-02 的有意选择：「记忆跑丢」是最坏故障，所以不设「按包位置反推」这种隐式默认。

优先级：
- 数据根：`--data-root` > `MINGMEM_DATA` > `MEM_DATA`（兼容旧名）> 配置文件
- 命名空间：`--ns` > `MINGMEM_NS` > 配置 `default_ns` > 按**当前目录名**反推 `project:<目录名>` > `global`

取向：**项目层做默认，`global` 必须显式写** —— 防止某个项目的噪声被自动升级成跨项目画像。

## 3. 命令速查

| 命令 | 一句话 | 会不会写数据 |
|---|---|---|
| `init` | 把数据根写进用户级配置 | 写配置，不写记忆 |
| `add` | 追加一条记忆事件 | **写** |
| `recall` | 结构化 briefing（六段） | 默认写一条 `access`；`--dry-run` 不写 |
| `search` | 原始 BM25/向量命中，调试用 | 不写（`--include-ask` 会写 consent 审计） |
| `links` | 按 id 精确看节点、边、双时态、回收站状态 | 不写 |
| `forget` | 软删 → 进回收站 | **写** `forget` 事件 |
| `bin` | 列出回收站 | 不写 |
| `restore` | 从回收站恢复 | **写** `restore` 事件 |
| `purge` | 真删（物理重写事件流） | **写** `purge` 审计事件（不可逆） |
| `cycle` | 遗忘扫描 + 报出待巩固/待熏习批次 | 默认**写** `sweep`/`archive`；`--dry-run` 不写 |
| `consolidate` | 把 ≥2 条来源巩固成一张语义卡 | **写** |
| `correct` | 追加更正（不改历史） | **写** |
| `rebuild` | 从事件流全量重建投影 | 只重写 `index.sqlite` |
| `verify` | 校验事件哈希链（改/删/插都能抓） | 不写；`--pin` 会写锚点文件 |
| `serve` | 第二层：常驻 JSON Lines 服务 | 不写；内部每条请求各写各的 |
| `import` | 从 v1 旧库（SQLite）一次性导入 | **写**（批量追加事件 + 重建投影） |
| `capabilities` | 能力探测：命令/限额/错误分类/层 | 不写（无需数据根） |
| `describe` | 命令与参数的机器可读描述 | 不写（无需数据根） |
| `status` | 统计摘要 | 不写 |
| `export` | 导出人读视图（md / obsidian） | 写导出文件，不写记忆 |
| `doctor` | 只读体检 + 事件↔投影对账 | 不写 |
| `selftest` | 临时数据根跑完整体检 | 不碰真实库 |

## 4. 逐条命令

### 4.1 init —— 初始化数据根

```
mingmem init --data-root <目录> [--default-ns NS] [--force]
```

- `--default-ns` 一般给 `project:<名>`；不给就按当前目录名反推。
- 已存在配置时退出码 2，提示「要改数据根请加 `--force`」。
- 只会建 `<数据根>/events/`，不写任何记忆。

### 4.2 add —— 写一条记忆

```
mingmem add --text <正文|-> [--kind episode] [--ns NS] [--tags a,b] [--entities x,y]
            [--refs id1,id2] [--disclosure public|ask|private] [--source user|ai|mixed]
            [--client-key KEY]
            [--S 0-1] [--D 0-1] [--E 0-1] [--C 0-1] [--I 0-1] [--dry-run] [--json]
```

- `--text -` 从标准输入读正文：`echo "笔记：..." | mingmem add --kind note --text -`
- 可用 `--kind`：`episode / note / feel / prefer / decide`（内部类型 `consent / forget / restore / purge` 不许手写；`correction` 用 `correct`；语义卡用 `consolidate`）。
- `--refs` 必须指向**已存在**的 id，否则退出码 2 并列出缺失项。
- 六变量不传就用该类记忆的默认值（附录 C）。传了会被夹到 `[0,1]`。
- `--dry-run` 只打印将写入的事件 JSON，不落盘。
- `--client-key` 是**幂等键**：同一个 key 再调不会写第二条，返回原 id 并标 `idempotent: true`（重试/重放安全）。

一条成功的 `add --json` 输出：

```
{
  "id": "epis-261026231324-bb13",
  "ts": "2026-10-26T23:13:24.050+08:00",
  "ns": "project:demo",
  "kind": "episode",
  "tags": ["架构", "事件流"],
  "entities": ["mingmem", "SQLite"],
  "refs": [],
  "disclosure": "public",
  "source": "user",
  "chars": 29
}
```

### 4.3 recall —— 结构化 briefing

```
mingmem recall --query <词> [--ns NS] [--scope a,b|all] [--limit N] [--min-score X]
               [--include-ask] [--include-archived] [--dry-run] [--json]
```

- 范围默认 = 当前命名空间 + `global`；`--scope all` 表示全部命名空间（不推荐日常用，容易串味）。
- `--limit` 默认 5，上限 50：`--limit 999` 会告警并**按 50 执行**；`--limit 0` 告警后回退默认值；`--limit abc` 是 argparse 错误（退出码 2）。
- **返回条数常常少于 limit**：MMR + 硬簇上限（同一近重复簇最多 2 条）宁可少给也不拿近重复凑数。调用方不要假设「一定有 5 条」。
- `--min-score`（0.2.1 新增）：检索**证据**门槛，默认取 `settings.MIN_SCORE`（0.28）；`0` 关闭分数地板。
  证据 = IDF 加权查询覆盖率，**不看融合分** —— 融合分里含 recency/E/S 偏置，图扩散邻居实测也能到 0.8 量级，
  按它设阈值等于没设。加了门槛的后果是**常见词/2 字查询可能只给 0~1 条**：查「的」返回 0 条是对的。
- `--min-score 0` 也不能让「零证据」条目回来：那只关掉分数地板，词面证据为零（没出现任何查询词）的条目
  仍然不返回。要「什么都看看」用 `search`（原始命中，调试用）。
- JSON 的 `items[]` 多了两个字段：`evidence`（证据分，0 表示纯图扩散补位）、`filler`（true = 补位线索，不是词面命中）；
  顶层多了 `gate`（`candidates / lexical / dropped_no_evidence / dropped_score / filled`），用来解释「为什么只给了这几条」。
- `--include-ask` 展示 `ask` 级记忆时**必然**在 stderr 留一行同意记录，并追加一条 `consent` 审计事件（事件里有 query、理由、被展示的 id）。
- `--include-archived` 把已归档（`storage<0.1 且 retrieval<0.05`）的也纳入检索。
- `--dry-run` 不写 `access` 事件（只读）。

### 4.4 search —— 原始命中（调试）

```
mingmem search --query <词> [--ns NS] [--scope ...] [--limit N] [--include-ask] [--include-archived] [--json]
```

打印 BM25 与向量两条通道的原始排名与分数，**不做 briefing、不做 MMR**，所以会出现同簇多条。
排查「为什么这条没被召回」用它；给用户看用 `recall`。

### 4.5 links —— 按 id 精确访问

```
mingmem links --id <id> [--json]
```

显示命名空间、类型、时间、披露等级、来源、原文、六变量当前值、强度（storage/retrieval/last_access/archived/superseded）、有效区间、出边/入边。
在回收站里的条目会多一行：

```
- 状态：**在回收站**（2026-10-26T23:13:25.934+08:00）；检索与导出都看不到它，只有 bin / links 能查到
```

找不到 id 时退出码 2：`错误：找不到节点：nope-000000-0000`。

### 4.6 删除与回收站（两层）

```
mingmem forget  --ids <id[,id]> [--reason 文本] [--ns NS] [--dry-run]   # 第一层：软删
mingmem bin     [--json]                                                # 只有这条路能看见已删项
mingmem restore --ids <id[,id]> [--ns NS] [--dry-run]                   # 撤销软删
mingmem purge   --ids <id[,id]> [--yes] [--dry-run]                     # 第二层：真删（不可逆）
```

- **软删后没有任何检索旁路**：`recall` / `search` / `export` 都看不到它，`--scope all`、`--include-archived`、`--include-ask` 也都不行（删掉的东西又混进检索就是污染）。唯一入口是 `bin` 与按 id 精确访问的 `links`。
- **真删必须先软删**：对活数据直接 `purge` 会被拒（退出码 2：「这些记忆还没软删，不能直接真删」）。
- `purge` 不带 `--yes` 只干跑：`将真删 1 条（不可逆）：<id>；确认请加 --yes`。
- `purge` 成功的样子：`已真删 1 条：移除事件 1 条、清理引用 6 条；审计事件 purg-...`
- 真删会**物理重写事件文件**（临时文件 + fsync + os.replace），只留一条 `purge` 审计事件，内含**条数**与 **id 的 sha256 前 16 位**，不留 id 本身 —— 所以事件流里再也查不到被删对象，但仍可核对「某条是否曾被真删」。
- 已软删的再 `forget` 会退出码 2（`已在回收站 1 条`）；不在回收站的 `restore` 会退出码 2。

### 4.7 cycle —— 一次维护

```
mingmem cycle [--ns NS] [--kinds episode,note] [--dry-run] [--json]
```

一次做三件事：遗忘扫描（`retrieval × 0.95`，越过阈值转归档）、报出待巩固批次（同一命名空间 ≥3 条未巩固 `episode`）、报出待熏习候选（同一标签 ≥3 次 `prefer`）。

```
记忆维护 cycle
- 遗忘扫描：retrieval × 0.95，覆盖 9 个节点（范围：全部命名空间）；本次归档 0 个
- 待巩固批次（同一命名空间 ≥3 条未巩固 episode）：
   · project:demo：4 条 → consolidate --from epis-...-3e3a,epis-...-bb13,epis-...-f2dd,epis-...-62b4 --text ...
- 待熏习候选（同一标签 ≥3 次 prefer）：
   （无）
- 提示：consolidate 由会话里的 AI 读本报告后写回；原始 episode 永不删除。
```

**它只报「该巩固了」，不替你写语义卡** —— 巩固需要读内容做归纳，属于会话里 AI 的活。

### 4.8 consolidate —— 巩固成语义卡

```
mingmem consolidate --from <id1,id2[,...]> --text <归纳后的正文>
                    [--kind semantic|preference|skill] [--ns NS] [--tags a,b]
                    [--disclosure ...] [--force] [--dry-run] [--json]
```

- 至少 2 个来源；来源必须存在、且**同属一个命名空间**（跨命名空间会要求显式 `--ns`）。
- 已巩固过的来源再巩固会被拒（`来源已巩固：…（如需重做请加 --force）`）。
- 产出节点的 `kind` 是 `semantic / preference / skill`，事件类型是 `consolidate`，来源 id 记在 `refs` 里。
- **原始 episode 永不删除**：巩固是「加一层结论」，不是「替换证据」。

### 4.9 correct —— 更正（双时态）

```
mingmem correct --target <id> --text <新的说法> [--ns NS] [--tags a,b] [--disclosure ...] [--dry-run]
```

```
$ mingmem correct --target epis-261026231323-3e3a --text "更正：投影重建要先备份 index.sqlite。"
已追加更正 corr-261026231325-380f：曾「今天把记忆内核的投影重建了一遍，确认事件流是唯一真…」→ 现「更正：投影重建要先备份 index.sqlite。」（历史未改）
```

被更正的节点会被打上 `superseded=1 / superseded_at / valid_to`，默认不再参与检索；原文永久保留，用 `links --id` 可追溯。briefing 的 ③ 现状段会显示「曾经：<旧说法>」。

### 4.10 rebuild —— 重建投影

```
mingmem rebuild [--json]
```

从事件流全量重放，重写 `index.sqlite`。**没有 `--ns`**（投影是整库的）。
什么时候用：投影文件被删/损坏、换机器、schema 升级、`doctor` 建议重建。

### 4.11 status —— 统计摘要

```
mingmem status [--json]
```

```
记忆内核状态
- 数据根：D:\MemoryData
- 事件：2 个文件 / 21 行（坏行 0）；节点 10 个（归档 0）
- 命名空间：project:demo=9；global=1
- 记忆类型：episode=3；note=2；correction=1；decide=1；feel=1；prefer=1；semantic=1
- 待巩固批次：0 个；向量：0 条（通道未启用（按设计暂不使用；计划 2300+ 条后再引入））
```

`--json` 里有 `data_root / events_files / events_lines / bad_lines / nodes / archived / by_ns / by_kind / pending_batches / vectors / vector_*`。
数据根后面出现「（投影刚重建）」= 这次是它顺手建的投影。

### 4.12 export —— 导出人读视图

```
mingmem export [--out 路径] [--ns a,b] [--kind a,b] [--tag a,b] [--exclude-tag a,b]
               [--title 标题] [--order asc|desc|section] [--lean] [--no-meta] [--toc]
               [--format md|obsidian] [--include-private] [--include-ask] [--json]
```

- 默认输出 `<数据根>/memory.md`，`--order desc`（时间倒序）。
- **默认排除 `private` 与 `ask`**；要含 `ask` 必须显式 `--include-ask`（会写 consent 审计）。
- `--lean` 只留时间/类型/正文；`--no-meta` 连抬头与标签也去掉；`--toc` 按正文里的 `##` / `###` 生成目录。
- `--order section` 按「第0-1节」这类标签的章/节顺序排，适合把课程笔记导成一本书。
- `--format obsidian` 加 frontmatter 与标签/双链。

### 4.13 verify —— 事件链校验

```
mingmem verify [--ns NS] [--pin <数据根之外的文件>] [--json]
```

```
事件链校验 verify
- project-demo.jsonl：5 行，入链 5 条，链完整 ｜ head 685141a352965992
- 锚点：未提供（本地链发现不了「整条链被重算」；要防它用 --pin <数据根之外的文件>）
- 结论：通过
```

- 能抓到：**等长改写**（断点落在被改行的**后继行**）、**删行**、**插行**、**剥掉 prev_hash**、**改历史行**（锚点失配）。
- 抓不到：**改最后一行**（没有后继行引用它）、**整条链被重算**。这两种只有 `--pin` 的外部锚点能发现：
  ```
  mingmem verify --pin D:ackupmingmem-pin.json   # 文件不存在 → 写入当前 head
  mingmem verify --pin D:ackupmingmem-pin.json   # 文件存在 → 逐个比对
  ```
- `purge` 重写事件文件后会自动重串链，所以真删之后 `verify` 仍然通过。
- `doctor` 里也会打印一行「哈希链：完整 / 断裂 N 处」，断裂时退出码 1。

### 4.14 serve —— 常驻服务（第二层接口）

```
mingmem serve --stdio
```

从标准输入按行读 JSON 请求，向标准输出按行写 JSON 响应（一行一个，不允许多行）。
请求里的 `args` 就是 CLI 参数，所以**不需要再学一套语义**：

```
{"id":1,"op":"ping"}
{"id":1,"ok":true,"code":0,"pong":true}
{"id":2,"args":["add","--text","常驻进程写的一条","--json"]}
{"id":2,"ok":true,"code":0,"out":"{...}","data":{"id":"epis-…"}}
{"id":3,"args":["recall","--query","常驻","--json","--dry-run"]}
{"id":3,"ok":true,"code":0,"out":"{...}","data":{"count":1,…}}
{"id":4,"args":["frobnicate"]}
{"id":4,"ok":false,"code":2,"out":"","err":"usage: mingmem …"}
{"id":9,"op":"exit"}
{"id":9,"ok":true,"code":0,"bye":true}
```

- 响应字段：`id`（原样回显）、`ok`（退出码是否为 0）、`code`（原始退出码）、`out`（CLI 原样输出）、
  `data`（`out` 能解析成 JSON 时才有）、`err`（stderr 非空时才有）。
- §4 的每条命令都能这样调：把命令行拆成字符串数组塞进 `args`。
- 每条请求内部**各加各的锁**，所以服务可以长驻；需要真并发就开多个进程，别开多个线程共用一个数据根。
- 进程启动时的数据根会传给后续请求；请求里带 `data_root` 可以覆盖。
- 读到 EOF 或收到 `{"op":"exit"}` 就退出；没有 HTTP，也没有网络监听。

Python 调用方用第三层更方便（同一个数据根），见 §10。

### 4.15 import —— 从 v1 旧库迁移

```
mingmem import <旧库数据根或 index.sqlite> [--ns-map project:旧=project:新] [--limit N] [--dry-run] [--json]
```

v1 的真相源是 `index.sqlite` 里的 `nodes` / `edges`；v2 的真相源是事件流。
所以迁移＝**把行翻译成事件再重放**，旧库只读、不改、不覆盖。

```
$ mingmem import D:\...\学习库\_Data --dry-run
（--dry-run，未写入）将导入 节点 59 条 / 边 118 条（跳过已存在 0）
- 旧库：D:\...\学习库\_Data\index.sqlite
- 命名空间：project:学习=59

$ mingmem import D:\...\学习库\_Data
已导入旧库：D:\...\学习库\_Data\index.sqlite
- 节点 59 条（跳过已存在 0）；边 118 条
- 命名空间：project:学习=59
- 投影：节点 59 ｜ 边 118 ｜ 已重建
```

**保真度**（这是迁移的全部意义，别只看条数）：
- 原始 `id / ts / ns / kind / text / tags / entities / refs / disclosure / source` 全部照搬；
- **强度与状态** `storage / retrieval / last_access / archived / superseded / consolidated` 一并保留
  （已归档的仍是归档、已被更正的仍是 superseded）—— 否则重建后旧库里压下去的东西会重新冒出来；
- 边的 `kind` 与 `weight` 保留（绝对赋值，不叠加）。

**幂等**：事件 id 已存在就跳过，重复跑不会翻倍（第二次会报「节点 0 条（跳过已存在 177）」）。
**命名空间映射**：旧库 `project:学习` 想并到 `global` 或改名，用 `--ns-map project:学习=project:coding`。
**跨机器**：旧库与目标数据根不必同盘；迁移完 `doctor` + `verify` 都应通过。

### 4.16 doctor —— 只读体检

```
mingmem doctor [--json]
```

```
记忆内核体检 doctor
- 脚本：<仓根>/mingmem/settings.py
- 库根：<仓根>
- 数据根：D:\MemoryData（存在；来源 配置文件 C:\...\config.json）
- Python：3.13.15 ｜ C:\...\python.exe
- SQLite：3.50.4 ｜ FTS5：可用
- 事件流：2 个文件 / 21 行 / 5067 字节；坏行 0
- 投影：D:\MemoryData\index.sqlite ｜ 节点 10 ｜ 边 4 ｜ 最新
- 事件↔投影对账：一致（节点 10）
- 稠密通道：已启用（bge-small-zh-v1.5 (int8 onnx) ｜ dim 512 ｜ fp32 ｜ onnxruntime <版本> / numpy <版本> ｜ 已向量化 10/10 条）
- 结论：通过
```

退出码：0 通过、1 发现问题（坏行、投影缺失节点等）、2 没有配置数据根。
对账不一致时会打印 `缺失事件：<id> ｜ <文件>:<行号>` —— 这是「事件流有、投影里没有」的铁证。
**空数据根**（刚 `init`、还没写入任何记忆）也返回 0，稠密通道那行显示 `已向量化 0/0 条`；
`doctor` 是纯只读：不会替你生成 `index.sqlite`（那是第一次写入/`rebuild` 的事）。
（没装 onnxruntime 时该行变成 `- 稠密通道：不可用（…）⇒ 已降级为 BM25 + 图扩散`。）

### 4.17 selftest —— 装好没有

```
mingmem selftest [--json]
```

在临时数据根跑 81 项闭环（写入、六段、隔离、双时态、签名、对账、单字查询、回收站、无配置退出码、空库体检、真实库零改动…），
**不碰真实库**，未配置数据根也能跑。看到 `合计 81/81 项通过`（装了 onnxruntime 时同样是 81/81，只是多走稠密通道） 才算装好。

## 5. 五个典型工作流

### 5.1 一次会话的记忆闭环

```
add（关键决定 / 发现 / 偏好）→ cycle（看该不该巩固）→ consolidate（写语义卡）→ 下次 recall 先看 ③ 现状
```

会话里的经验写 `episode`；稳定的结论写 `decide` / `prefer`；跨会话可复用的规律用 `consolidate` 升成 `semantic`。

### 5.2 纠错（不留假历史）

新事实和旧记忆冲突时**不要**改旧文本，用 `correct --target <旧 id>`。这样能同时回答「现在是什么」和「以前是什么」。

### 5.3 删错了怎么办

```
bin                      # 先看回收站里是哪条
restore --ids <id>       # 撤销软删，立刻又能被检索到
```

真删（`purge --yes`）之后**没有任何恢复手段** —— 事件流里的行被物理移除，只剩一条哈希审计。

### 5.4 换机器 / 迁移

拷**整个数据根**（`events/` 必须有，`index.sqlite` 可以不拷）。到新机器上 `init --data-root <新路径>`，然后 `doctor`；
若投影缺失或签名不对，`rebuild` 会全量重放事件流。**不要手工编辑 `events/*.jsonl`**。

### 5.5 定期导出

```
mingmem export --lean --out D:\MemoryData\memory.md
mingmem export --format obsidian --out <库>\记忆.md
```

导出只是**可重建视图**，不是真相源；删掉随时能再导。

## 6. 与 AI 会话协作的口径

1. **写入方**：会话里决定「这条值得记」的永远是 AI 或用户；内核不主动采集。
2. **必给 `--ns`**：项目会话给 `project:<名>`，跨项目约定才给 `global`。
3. **一次会话结束前**跑一次 `cycle`，把「待巩固」写成交接或语义卡。
4. **召回先看 ① 和 ⑥**：① 说明范围对不对，⑥ 说明为什么召回它；范围不对先改 `--scope` / `--ns`，不要急着调 `--limit`。
5. **不要把 `--include-ask` 当默认**：它每次都会留审计记录，等于把「你让我看了什么」写进事件流。
6. **结论优先、证据在后**：briefing 的 ③ 现状段就是给「先给结论」用的；② 时间线是证据。

## 7. 脚本与批处理

- 机器可读统一用 `--json`。支持 `--json` 的命令：`add recall search status doctor consolidate correct cycle rebuild export links forget bin restore purge`；未支持的命令会往 stderr 打一行告警，然后照常输出文本。
- 干跑优先：`add / forget / restore / purge / consolidate / correct / cycle / recall` 都有 `--dry-run`（`purge --dry-run` 不带 `--yes` 就是干跑）。
- 判断成功看**退出码**，不要靠 grep 输出。**反面教训**：我们的评测脚本曾给一个不支持 `--quiet` 的工具加上 `--quiet`，argparse 直接退出码 2、什么都没跑，而旧报告文件还在，看起来像通过了。
- 并发：多条命令可以同时跑，内核用数据根级锁串行化写。但**不要**同时 `purge` 与 `add`（真删要重写事件文件），也不要把同一条记忆交给两个进程同时 `correct`。
- 批量写入：用 `--text -` 从 stdin 读，避免命令行转义地狱。

## 8. 维护节奏

| 时机 | 命令 | 目的 |
|---|---|---|
| 每次会话结束 | `cycle` | 遗忘扫描 + 看该不该巩固 |
| 巩固之后 | `recall --query <新结论> --dry-run` | 确认语义卡能被召回 |
| 每周 / 大量写入后 | `doctor` | 对账，早发现投影漏节点 |
| 换机器、删过 `index.sqlite`、schema 升级后 | `rebuild` | 从事件流重建投影 |
| 升级代码后 | `selftest` + `eval --gate` | 81 项闭环 + 检索质量门禁不退化 |
| 定期 / 换机器后 | `verify --pin <数据根之外的文件>` | 事件链是否被动过 |
| 定期 | `export --lean` | 一份能直接读的备份视图（不是备份本身） |

真正的备份是**整个 `events/` 目录**：它是唯一真相源。

## 9. 十条常见误用

1. **假设 `recall` 一定返回 5 条** —— 去冗余会少给，甚至给 0 条。
2. **用 `--scope all` 当默认** —— 会把别的项目的噪声混进来。
3. **手工编辑 `events/*.jsonl`** —— 你能改，但会破坏投影签名与对账；要改内容用 `correct`。
4. **直接 `purge` 活数据** —— 被拒（退出码 2），而且真删不可逆。
5. **以为软删就等于删了** —— 事件流原文还在；要真删必须 `purge --yes`。
6. **把 `ask` 级的记忆默认展示** —— 每次展示都会留审计，且必须能解释理由。
7. **用 `add --kind correction`** —— 请用 `correct --target`，否则不会产生双时态。
8. **把语义卡当证据** —— 语义卡是结论，证据在它 `refs` 指向的 episode 里。
9. **忘了 `-X utf8`** —— Windows 上会出现编码错误或乱码。
10. **把导出文件当真相源** —— 它是可重建视图，删掉不心疼；`events/` 才是。

## 10. 给别的项目 / Python 调用方（第三层接口）

**CLI 是一等公民，别把内核当库直接 import 内部模块。** 两条正式接法：

```python
from mingmem.api import MemoryCore, MingmemError

core = MemoryCore(data_root=r"D:\MemoryData", ns="project:demo")   # 数据根也可省略（走配置/环境变量）
added = core.add("决定把内核做成插件内核", kind="decide", tags=["架构"])
briefing = core.recall("插件内核", limit=5, dry_run=True)           # dry_run=True 不写 access 事件
try:
    core.links("nope-000000-0000")
except MingmemError as exc:                                        # code 就是 CLI 退出码
    print(exc.code, exc.message)
```@

- 方法名 = 子命令名：`add / consolidate / correct / forget / restore / purge / recall / search /
  links / status / bin / verify / cycle / rebuild / doctor / export / selftest`。
- 返回值 = 那条命令的 `--json` 结构（`selftest` 返回文本）。**失败一律抛 `MingmemError`**，不返回空值装成功。
- 必须自己给 `ns`（或构造时传 `ns`），内核不会猜你的项目名。
- **不要假设 `recall` 恒返回 5 条**（去冗余会少给，甚至 0 条）。

需要「每次调用都免进程启动」时用第二层 `serve --stdio`（§4.14）；两种接法背后是同一条 CLI，
所以行为、退出码、审计记录完全一致。跨语言就只认 JSON Lines，别去解析 `out` 的文本排版。
