# mingmem 设计文档

> 本文只讲**为什么这么设计**。用法见 `操作手册.md`，坑点见 `异常与附录.md`。
> 旧库 `Projects/记忆内核/记忆内核库/` 已按 D-03 冻结为档案，不再是实现载体。

## 1. 一句话架构

**append-only 事件流是唯一真相源；SQLite 只是可随时丢弃重建的投影。**
任何"读不到 / 不一致 / 怀疑坏了"的问题，答案都是 `rebuild`（或让 `doctor` 告诉你缺了什么）。

~~~~
            add / consolidate / correct / cycle / recall(access)
                              │
                              ▼
        events/<ns>.jsonl   （只追加、不改写、带 fsync）
                              │  replay（按绝对时刻排序）
                              ▼
        index.sqlite  nodes / edges / nodes_fts / meta（可删可重建）
                              │
                              ▼
        recall → 六段 briefing（结构化，不是片段堆叠）
~~~~

## 2. 分层

| 层 | 模块 | 职责 | 不允许做的事 |
|---|---|---|---|
| 常量 | `settings.py` | 全部可调参数、枚举、schema 版本 | 依赖其他业务模块 |
| 配置 | `config.py` | 用户级配置（数据根 / 默认命名空间）、数据根解析顺序 | 碰事件或投影 |
| 基础 | `text.py` `decay.py` | 时间、分词（中文 bigram）、id、命名空间、六变量与衰减 | 碰数据库 |
| 存储 | `store.py` | 数据根、命名空间文件、**加锁 + 原子 append**、**投影签名** | 解析业务语义 |
| 链 | `chain.py` | `prev_hash` 计算、链校验、purge 重串、链头锚点（pin） | 碰数据库、解析命令行 |
| 投影 | `projection.py` | schema、`apply_event`、重放、增量、签名对账 | 决定"该不该写"（那是命令层的事） |
| 检索 | `retrieve.py` `vector.py` | BM25 / 图扩散 / 向量、RRF 融合、过滤条件 | 生成最终文案 |
| 输出 | `briefing.py` `render.py` | 六段 briefing、导出视图（md / obsidian） | 直接写事件 |
| 业务 | `core.py` `commands.py` | 批次、熏习、对账、真删重写、18 个命令的业务体 | 解析命令行参数 |
| 入口 | `cli.py` `__main__.py` | argparse、命令级加锁、分发、退出码 | 承载业务逻辑 |

依赖方向单一向下；`commands`/`render` 反向要 `cli` 的 `emit/fail` 时，用 `cli.main` 内的**局部 import** 断环（顶层无环）。

## 3. 事件模型

一行一个 JSON，字段：`id / ts / ns / kind / text / tags / entities / refs / disclosure / source / prev_hash`，可选 `S D E C I`。

| kind | 由谁写 | 进节点表 | 说明 |
|---|---|---|---|
| `episode` `note` `feel` `prefer` `decide` | `add` | ✅ | 原始记忆 |
| `consolidate` | `consolidate` | ✅（节点 kind = `node_kind`） | 巩固出的结论（`semantic` / `preference` / `skill`） |
| `correction` | `correct` | ✅ | 更正；同时给被更正者封 `valid_to` |
| `access` | `recall` | ❌ | 访问痕迹 → 重置检索强度、强化共现边 |
| `sweep` `archive` | `cycle` | ❌ | 遗忘扫描 / 归档 |
| `link` | 显式建边 | ❌ | 显式关系 |
| `consent` | `recall/search/export --include-ask` | ❌ | **审计**：谁在什么时候同意展示哪些 ask 记忆 |
| `forget` `restore` | `forget` / `restore` | ❌（只改标记） | 回收站：`erased=1/0`，原文不动 |
| `purge` | `purge --yes` | ❌ | 真删后的审计：只有条数与 id 的 sha256 前 16 位 |

**审计类事件不许手写**：`add` 拒绝 `consent/forget/restore/purge`（以及 `access/sweep/archive/link/correction/consolidate`）—— 否则调用方可以伪造「用户同意了」「这条已真删」的记录，审计就失去意义。

**为什么强度变化也写事件**：只有把 `access`/`sweep`/`archive` 也落成事件，`rebuild` 才能连"记忆的强弱"一起复原 —— 否则重建后排序会变。

## 4. 双时态与更正（G05）

`correct --target <id> --text ...` **不改历史**：

1. 追加一条 `correction` 事件（`refs=[target]`）；
2. 投影里给 target 置 `superseded=1`、`superseded_at=ts`、`valid_to=ts`；
3. 检索条件默认带 `COALESCE(superseded,0)=0` ⇒ 旧事实不再参与排序；
4. 旧节点**原文永久保留**，`links --id` 可精确追溯（这是审计路径，不是检索路径）。

所以"现在是什么"与"曾经是什么"是两套数据：检索给现在，`links`/`export` 给历史。

## 5. 披露等级与同意（G20）

- `private`：默认不进检索、不进导出。要取出必须显式 `--include-private`。
- `ask`：默认同样不出现；要出现必须显式 `--include-ask`，**并且**每次实际展示了 ask 条目都会追加一条 `consent` 事件（含 `query`、`targets`、`reason`），输出里带 `ask_audit`。
- `public`：无限制。

设计取向：**"不给"是默认，"给"要留痕**。同意不是一次性的全局开关，而是逐次记录。

## 6. 写入原子性（G27）

| 措施 | 为什么 |
|---|---|
| 单次 `os.write` + `O_APPEND` | 保证整行落在文件末尾，不会与别的进程交错 |
| `fsync` | 进程崩溃后事件不只在页缓存里 |
| 数据根**命令级可重入锁**（`os.mkdir` 原子建目录） | 关键：只锁 `append` 不够 —— 两个进程同时首次建投影会互相删 `index.sqlite`（实测 10 并发时 9 个失败） |
| **持锁期间心跳**（后台线程每 `LOCK_STALE/3` 刷新锁目录 mtime） | 补救性修复，见下：残留判据与持锁时长必须解耦 |
| 锁超时 10s / 残留 5s 自动清 | 残留锁（进程被杀）5 秒后自动清，不永久阻塞；**仍在跑的锁靠心跳续命，不会被误清** |
| `selftest` 不持锁 | 它要起子进程，父进程持锁会与子进程互锁 |

**为什么需要心跳（实测缺陷，2026-10-26 修）**：`LOCK_STALE` 的本意是"进程崩了留下的锁"，
但命令级加锁把**整条命令**包在锁里，`rebuild` / `purge` / `cycle` / 大库 `export` 的持锁时长
可以远超 5 秒。实测：持锁进程还在跑，第二个进程在 5.0 秒后把锁目录当残留删掉并自己抢锁
⇒ **两个进程同时持锁，互斥形同虚设**（可能丢事件、撕坏事件文件）。修法是后台线程定期
`os.utime` 锁目录；进程真死时心跳消失，残留清理逻辑照旧生效（已验：kill -9 后 5 秒可重新拿锁）。

## 7. 投影签名与对账（G28 / G43）

签名 = 逐事件文件 `[文件名, 字节数, 纳秒 mtime, 末行 sha256 前 16 位]` 的 sha256。
旧实现用 `[字节数, 秒级 mtime]`：同一秒内的等大小改写算不出变化 ⇒ 投影过期却被当成"最新"。

签名只是**快速判据**；最终防线是 `doctor` 的**事件↔投影对账**：从事件流推出"应有节点 → (文件, 行号)"，与投影逐 id 比对，不一致就以退出码 1 指认
`缺失事件：<id> ｜ 文件:行号`。**投影是派生视图，事件流才是真相源** —— 这条不变量靠对账守，不靠签名守。

### 7.1 事件哈希链（G44）

签名与对账都只回答「投影是不是最新 / 有没有漏应用事件」，**都假定事件流本身没被改过**。
哈希链补上这一层：每条事件带 `prev_hash`。

- **链值**：上一条事件**原始字节**（不含行尾换行）的 sha256。第一条入链事件是 `GENESIS`；
  若它前面已有升级前写入的历史行（无 `prev_hash`），则锚定「此前所有非空行」的前缀摘要 —— 历史行也被覆盖进来。
- **空行与坏行**：空行不入链也不计入前缀；坏行（非 JSON）原样保留、不入链，链会跨过它。
- **`verify`**：逐文件走一遍，断点精确到 `文件:行号`，并给出每个文件的 head。异常形态都能抓：
  等长改写（断点落在**后继行**）、删行、插行、把 `prev_hash` 剥掉、改历史行（锚点失配）。
- **`purge` 必须重串链**：删行会让后续行的 `prev_hash` 全部对不上，所以真删重写时从 `GENESIS`
  重串（坏行仍原样保留）。真删本身就是一次被审计的、有意的重写。
- **两条抓不到的情况（必须说清）**：
  1. **改最后一行**：没有后继行引用它 —— 只有 `verify --pin` 的头部锚点能抓；
  2. **整条链被重算**：攻击者能从 `GENESIS` 起重算全部 `prev_hash` —— 本地任何校验都抓不到，
     只有把 head 摘要**放到数据根之外**（`--pin <文件>`）才能发现。

## 8. 检索管线

~~~~
query
 ├─ 分词：查询侧中文 bigram + 英文按词；索引侧额外写中文单字（让单字查询可命中）
 ├─ BM25（FTS5）            ┐
 ├─ 向量（可选；未装依赖则跳过） ├─ RRF 融合 → 重排（新近/E/S/retrieval）
 └─ 图扩散（共检索边 1~2 跳）  ┘        ↓
                          证据门槛（0.2.1）→ 截断（默认 5，上限 50）→ MMR 去冗余
后处理：命中节点 on_access（storage↑，retrieval=1），同时命中者两两加边（LTP）
~~~~

### 8.1 证据门槛为什么不挂在融合分上（0.2.1）

实测：查「笔记」时真命中只有 1 条，另外 4 条是图扩散邻居，融合分 **0.8300 / 0.8252 / 0.8205 / 0.8159**，
与真命中的 **0.8300** 几乎重合。原因有两层：融合分里 `W_REC=0.20` 的新近项对同一天写入的条目几乎相同；
`norm_channel` 是**逐通道独立归一化**，图扩散通道里排第一的邻居也能拿到 `norm=1`。
⇒ 任何按融合分设的阈值要么全留、要么全杀。所以门槛只看**检索证据**：

- `evidence` = IDF 加权查询覆盖率（只在本次检索范围内统计 df）；一次都不出现的查询词不进分母
  （长查询里大量是分词造出来的假 bigram，如「离线评测用不用」切出的「测用/用不」，让它们进分母等于
  让分词噪声决定门槛）。
- **边界/接缝**：中文 bigram 会把「记忆内核」切成 记忆｜忆内｜内核，查「忆内」也能命中真字符串。
  无词典时的判据是**用语料自己的词频反推**：若一次出现两侧的重叠 bigram 都是库里立得住的常用组合
  （df≥2），且查询词不比它们加起来更常见，则判为接缝，证据清零。
  「忆内」在「记忆内核」里 ⇒ 记忆/内核 都是常用词 ⇒ 判接缝；「偏好」在「用户偏好简短」里 ⇒
  户偏/好简 在库里立不住 ⇒ 判真词。单词语查询若只落在接缝上，直接不算证据（返回 0 条）。
- 两级门槛：绝对地板 `MIN_SCORE`，再叠加相对地板（本次最佳证据的 `REL_KEEP_RATIO`）压长尾。
- **图扩散只补位**：词面证据为零的候选不参与排序；只有当查询有 ≥2 个查询词且词面命中**恰好 1 条**时，
  才补 1 条图扩散线索（`filler=true`，永远排最后）。这样既保留"语义相关但用词不同"的桥接，
  又不让邻居占满 top5。
- 已知残留（不装词典就消不掉）：语料很小时（df 普遍为 1）接缝判定会退化为不判；
  「回忆内容」这种两侧都不是常用词的片段仍会命中。

过滤条件（默认）：`archived=0`、`superseded=0`、`disclosure<>'private'`、`disclosure<>'ask'`。
向量通道按量级阈值停用（`VECTOR_MIN_NODES=2300`）；阈值前 `--vector` 直接拒绝（退出码 2），不加载模型。

### 8.2 稠密通道（0.3.0，可选）

**模型**：bge-small-zh-v1.5 的 int8 ONNX 版，24MB，512 维，MIT 许可，随仓内置（`mingmem/dense/model/`）。
选它的理由：24M 参数 / 24MB 是"够用且带冗余"的甜点；再大就是百 MB 起，违背本地优先。

**分词器是自己写的**（`dense/wordpiece.py`，纯标准库）：BERT WordPiece 只有四步，200 行能写完，
换掉 `tokenizers`（7MB Rust 轮子）与 `transformers` 的整条依赖链。默认 `lowercase=True`：
上游 ONNX 端口的 `tokenizer.json` 写的是 `false`，实测那样 `SSH/APK/BERT` 全变 `[UNK]`，
核心集 recall 从 1.000 掉到 0.917 —— 宁可偏离那个产物，也要贴合 bert-base-chinese 的原始口径。

**确定性（踩过的坑）**：int8 动态量化按**批内激活范围**定标，同一句话放进不同批次余弦只有
**0.9954**（逐元素差 0.013），会让 `rebuild` 前后检索顺序漂移，直接违反"投影可重建"。
解决：**batch=1**（实测逐位一致，差 0.0）。代价是 160 条/秒而不是 1200 条/秒 ——
写入时向量化完全够用；10 万条整库重建是一次性十分钟级开销。

**录取门槛（0.3.0 的关键设计）**：绝对余弦阈值**不可用** —— 实测 bge-small 上
"同领域无关"的句子余弦也在 0.45~0.55，而 alias 用例的正确答案最低只有 **0.349**。
所以录取只看**名次**（向量前 5）＋一个宽松绝对下限（0.30），不做分数窗口。
推理侧另有一条：**没有内容词的查询不兜底**（「的」「怎么」仍返回 0 条），否则稠密通道会
永远给出"最近的 5 条"，把"宁可空、不可编"这条原则废掉。

**融合**：`W_RRF`/`W_CH` 是"没有向量"时调的，直接接上会让同义命中被词面噪声压住
（实测 alias 卡在 0.619）。改为按**名次衰减**的独立加分（`DENSE_W=0.45`，第 1 名满分、线性衰减到 0）。
注意：不能"只要出现在向量通道就给分"——61 条语料里向量会返回 51 个邻居，人人都加分 ⇒
相对次序不变、调权重完全无效（实测 0.35/0.7/1.0 指标一模一样）。

**写入即向量化**：统一在 `projection.apply_event` 里补（新增节点的事件都会走到），
重放（rebuild）期间关掉、末尾统一补。以前只在 `add`/`correct` 里补，`consolidate` 出的语义卡
没有向量 ⇒ rebuild 前后顺序不一致（被自检抓到）。

**降级**：缺 `onnxruntime`/`numpy`/模型文件时，`vector_available()` 为假，
检索与 0.2.x **逐位相同**；`doctor` 会写明原因，`--vector` 显式要求时返回 rc=2 而不是静默忽略。

## 9. 六段 briefing

① 主题与范围（含**绝对时刻**的时间跨度）→ ② 时间线（按绝对时刻排，带 refs 关联）→ ③ 现状（语义卡/偏好，带"曾经/现在"）→ ④ 相关实体 → ⑤ 情绪与偏好线索 → ⑥ 来源（id + ns + ts + 通道与分数，说明**为什么召回它**）。

限制：默认 ≤24 行；截断时按序丢弃尾部段落。

## 10. 衰减与遗忘

细节 `D(t)=D0·e^(-λD·t)`，`λD=λ0(1-αE)(1-βC)(1+γI)`；意义 `S`、情绪 `E` 各自更慢（`λE < λS < λD`）。
`cycle` 做一次遗忘扫描：`retrieval *= 0.95`；`storage < 0.1 且 retrieval < 0.05` ⇒ 归档（**不删事件**）。
存储强度只增不减（访问时 `storage += 0.05·(1-storage)`）⇒ "高存储低检索"＝存在但难找，命中即复活。

**排序用的是现值，不是入库值**（0.2.3 修）：重排项里 `W_E·E(t)`、`W_S·S(t)` 取 `decayed()` 的结果。
之前的实现用入库时的 E/S 打分，却用现值渲染简报，等于「显示的和排序的依据不是一回事」——
老化夹具实测：正文与 S 完全相同的新旧两条，400 天前那条重排分 0.577、今天那条 0.855（S 现值 0.108）。

## 11. 可验证性

- `selftest`：**76 项**，全部在临时数据根跑，跑前跑后比对真实库指纹（必须零改动）。
- `doctor`：只读体检；坏行、投影损坏、对账不一致、**哈希链断裂**都以退出码 1 报出。
- `verify`：事件链校验，断点精确到 `文件:行号`；`--pin` 把链头摘要锚到数据根之外。
- `mingmem/evalset/`：离线评测集（30 条用例 + recall@5 / mrr@5 / redundancy@5 / leak_count / section_fill）+ `--gate` 门禁。

## 12. 配置与数据根（D-02）

`mingmem init --data-root <目录> [--default-ns NS]` 写用户级配置；之后命令不再需要 `--data-root`。
解析顺序：`--data-root` > `MINGMEM_DATA` > `MEM_DATA`（兼容）> 配置文件；都没有则**退出码 2** 并打印修复命令。

命名空间同理：`--ns` > `MINGMEM_NS` > 配置 `default_ns` > 当前目录名（`project:<名>`）> `global`。
**取向：项目层默认，global 显式** —— 防噪声升级成画像。

为什么不做隐式默认：数据根一旦"猜错"，表现不是报错而是**记忆变空**，用户会以为丢了。
多一步 `init` 换「永不静默跑偏」，值得。

## 13. 删除与回收站（G14）

append-only 与「删除权」天然冲突，所以做成两层：

| 层 | 命令 | 事件 | 投影动作 | 能否恢复 |
|---|---|---|---|---|
| 软删 | `forget --ids` | `forget`（targets） | `erased=1`、`erased_at` | 可以（`restore`） |
| 真删 | `purge --ids --yes` | `purge`（只留条数与 id 哈希） | 重写事件流后 `rebuild` | **不可以** |

三条硬约束：
1. **没有检索旁路**：`filter_conds` 无条件带 `COALESCE(erased,0)=0`，`export_filter` 同样；
   `bin` 是唯一列表入口（`links --id` 属精确访问且会标注）。
2. **真删必须先软删**：`purge` 会检查目标是否在回收站，不在就拒绝 —— 防止误删活数据。
3. **审计只留哈希**：`purge` 事件里只有 `purged_count` 与 `purged_sha256`（id 的 sha256 前 16 位），
   id 本身不进事件流 ⇒ 「查不到被删对象」与「可核对是否曾删过」同时成立。

真删的写入安全：逐文件「临时文件 + `fsync` + `os.replace`」原子替换；失败清临时件并提示 rebuild。
坏行原样保留（不因一次清理丢掉证据），**重写后重串哈希链**（见 §7.1）。

## 14. 三层接口（D-07 / D-27）

| 层 | 形态 | 谁用 | 实现 |
|---|---|---|---|
| 1 | **CLI**（一等公民） | 人、脚本、看板 | `cli.py` + `commands.py` / `render.py` |
| 2 | `serve --stdio`（JSON Lines，协议 **mmp/1**） | 常驻宿主、别的语言的模块、插件壳 | `rpc.serve_stdio` |
| 3 | Python `MemoryCore`（通用 `call` + 糖） | 同进程、同语言的调用方 | `api.MemoryCore` |

**自描述是这套接口的地基**（新增于 0.2.0，0.2.1–0.2.3 沿用）：

- `spec.py`：命令**语义**表（summary/writes/remote/notes/examples）+ `capabilities()` / `describe()`。
- `describe()` 的**参数表直接从 argparse 抽**（walk `build_parser()` 的 actions），所以
  「文档里的参数」与「真正能用的参数」在构造上不可能不一致；自检里有一项专门比对两侧集合。
- `rpc.argv_from_params()` 把 `{参数名: 值}` 翻译成命令行；参数名 = argparse 的 dest。
  ⇒ **内核加参数不需要改接口层代码**，这正是「通用覆盖」而不是「一个命令一个方法」的原因。
- `api.MemoryCore.call(command, **params)` 是同一套东西的 Python 门面，糖方法只是它的薄包装。

**后两层是薄适配**：它们都调用同一个 `cli.main`，只做「参数拼装 / 结果取回 / 异常转换」，
**不复制任何业务逻辑**。代价是每次调用多一层函数开销（实测可忽略），换来的是「三层永远同一个行为」。

协议（`serve --stdio`，7 个 op：`hello / ping / capabilities / describe / call / batch / exit`）：

~~~~
→ {"id":1,"op":"hello","protocol":"mmp/1"}        ← {"v":"mmp/1","ok":true,"data":{"protocol":"mmp/1",…}}
→ {"id":2,"op":"capabilities"}                    ← {"ok":true,"data":{"commands":{…},"errors":{…},"limits":{…}}}
→ {"id":3,"op":"call","command":"add",
   "params":{"text":"…","tags":["a"]}}            ← {"ok":true,"data":{"id":"epis-…"},"meta":{"wrote":true}}
→ {"id":4,"op":"batch","items":[…]}               ← {"kind":"batch_partial","results":[…]}
→ {"id":5,"args":["status"]}                       ← 旧形态（等价于 CLI 参数数组）仍然兼容
→ {"id":9,"op":"exit"}                            ← {"ok":true,"bye":true}
~~~~

- 响应信封固定：`{v, id, ok, code, kind, retryable, data, text, err, meta}`；`kind` 是稳定枚举。
- **没有跨条目事务、不并发**：`serve` 逐条串行；要并发就开多个进程（数据根锁保证写安全）。
- 编码：服务端把 stdin/stdout **强制成 UTF-8**（协议自己的编码不跟控制台走）；CLI 文本输出仍跟随 locale。

`MemoryCore` 的约定：**失败抛 `MingmemError(message, code, kind, retryable)`**，不返回空值装成功；
`call(command, **params)` 是通用入口，糖方法（`add/recall/…`）只是它的薄包装。

完整的对外规则（信封字段表、错误分类、幂等、分页、并发、各类调用方接入清单、明确禁止）见
`docs/接口规范.md` —— **那是对外契约，这一节只是实现侧说明**。

## 15. 旧库迁移（v1 → v2）

v1 的真相源就是 `index.sqlite` 里的 `nodes` / `edges`（没有事件流）；v2 反过来。
所以 `import` 不是"拷文件"，而是**把行翻译成事件再重放**：

| v1 | v2 事件 | 保真点 |
|---|---|---|
| `nodes` 一行 | 一条节点事件（kind 原样：`episode/note/…/semantic/correction`） | `id/ts/ns/text/tags/entities/refs/disclosure/source` 照搬 |
| `nodes` 的强度列 | 事件的 `strength` 字段 | `storage/retrieval/last_access/archived/superseded/consolidated` 由 `insert_node` 直接写回投影 |
| `edges` 一行 | 一条 `link` 事件（`src`/`refs`/`edge_kind`/`weight`） | 边的 `kind` 与 `weight` **绝对赋值**（不是叠加） |

**为什么强度必须带过去**：投影的强度是靠 `access`/`sweep` 事件演化出来的。若迁移只写正文，
重建后所有节点强度会回到初始值 —— 已经归档的记忆重新可检索、已被更正的记忆重新成为"现状"。
那是**数据层面的倒退**，比丢一条更糟。

- 旧库**只读**（`mode=ro` 打开），不改旧库一个字节；旧库按 D-03 冻结。
- **幂等**：事件 id 已存在就跳过；边事件 id 由 `(src,dst,kind)` 的 sha1 决定，同一组合永远是同一条。
- 没有"保留旧库链接"的模式：迁移是一次性翻译，之后 v2 的事件流就是唯一真相源。
- 局限：v1 没有 `valid_from/valid_to`，双时态区间只能从导入时刻起算（`superseded` 状态本身是保真的）。

## 16. 已知未做（诚实清单）

1. **中文分词的残留问题**（0.2.1 部分解决，0.3.0 起由稠密通道兜住）：词面通道仍是 bigram、没有词表；
   但同义改写现在由稠密通道接住（alias 桶 0.381 → 0.905）。词面通道自身的接缝误判（小语料退化）**仍然存在** —
   它只是不再决定最终召回。
2. **哈希链的两条盲区**：末行改写、整链重算 —— 本地链抓不到，只能靠 `verify --pin` 的外部锚点。
3. **真删的跨文件非事务**：单文件原子替换；多文件之间极端中断会出现部分已清（用 `doctor` + `rebuild` 收敛）。
4. **`pip install -e .` 未实测**（`pyproject.toml` 已按标准补 `[build-system]`；接法仍推荐 `PYTHONPATH`）。
5. **稠密通道的性能边界**：160 条/秒（batch=1，确定性优先）；10 万条整库重建约 10 分钟。
   未做 ANN —— 10 万条以内暴力点积 10~30ms，够用；百万级要换索引与存储。
   int8 模型对批尺寸敏感这件事已用 batch=1 规避，但**换模型/换 onnxruntime 版本后要重跑评估**。
6. **`recency` 只验过同日内确定性**：跨天/跨月衰减未做长周期验证。
7. **评测门禁的破坏性验证只覆盖 `leak_count`**：`recall/mrr/redundancy` 越线分支未各自构造破坏用例。
