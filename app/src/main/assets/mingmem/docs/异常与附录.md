# mingmem 异常与附录

> 本文件**只给人（和接任的会话）读**；库内代码对它零引用。
> 前半是「出错时怎么判断、怎么修」，后半是查表用的附录（事件类型、字段、常量、已知限制）。
> 错误消息与退出码均为 2026-10-26 真跑抓取（Python 3.13.15 / Windows），未经验证的项一律标「未核」。

---

## 1. 退出码

| 码 | 含义 | 典型来源 |
|---|---|---|
| 0 | 成功 | 所有子命令 |
| 1 | 体检发现问题 | 仅 `doctor`（坏行、投影缺节点等） |
| 2 | 用法错误或前置条件不满足 | 没配置数据根、参数非法、argparse 校验失败、业务规则拒绝（如未软删就真删） |

**判成功只看退出码**，不要 grep 输出。协议层（serve / MemoryCore）还会给一个**稳定分类** @@kind@@
（@@usage/invalid/config/not_found/conflict/busy/storage/findings/unsupported/failed@@）与 @@retryable@@ 标志，
调用方认它、不解析中文。完整表见 @@docs/接口规范.md@@ §7。
argparse 的错误（缺参数、非法枚举值、`--limit abc`）同样是 **2**，但输出在 stderr 且以 `usage:` 开头 —— 它意味着**命令根本没执行**。

## 2. 错误消息速查

### 2.1 前置条件

| 消息（节选） | 场景 | 怎么办 |
|---|---|---|
| `未配置数据根：记忆无处安放，拒绝继续。`（附 3 行修复提示） | 从没 `init`，也没给 `--data-root` / `MINGMEM_DATA` | 跑 `mingmem init --data-root <目录>`；临时用可 `--data-root` |
| `已存在配置：<路径>；要改数据根请加 --force` | 重复 `init` | 确认要换根再加 `--force` |
| `建不了数据根：<路径>（<系统错误>）` | 目录不可写、盘符不存在 | 换目录或修权限 |

### 2.2 参数与业务规则

| 消息（节选） | 场景 | 怎么办 |
|---|---|---|
| `错误：consolidate 请用 consolidate 子命令（需要 --from 来源）` | `add --kind consolidate` | 用 `consolidate --from id1,id2` |
| `错误：不支持的 kind：<k>（可用：episode、note、feel、prefer、decide）` | 手写派生/审计事件类型（`access/sweep/archive/link/correction/consolidate/consent/forget/restore/purge`） | 用对应子命令：`correct` / `consolidate` / `forget` / `restore` / `purge`（**这些类型只能内核自己产生**，否则等于允许伪造「同意」「真删」记录） |
| `错误：正文为空：--text 必须非空` | 正文只有空白 | 给内容；注意 `--text` 不会自动 strip 掉有意义的前导空白 |
| `错误：refs 不存在：<ids>` | `--refs` 指向不存在的节点 | 先 `search` 或 `recall` 拿真 id |
| `错误：至少需要 2 个来源 id（--from id1,id2[,...]）` | `consolidate` 只给 1 个来源 | 补到 ≥2 条 |
| `错误：来源已巩固：<ids>（如需重做请加 --force）` | 同一批来源重复巩固 | 确认要重做再加 `--force`（会多一张卡，旧卡不删） |
| `错误：来源不存在：<ids>` / `错误：来源跨命名空间（…），请用 --ns 显式指定` | 巩固的来源跨 `ns` | 用 `--ns` 选定归属命名空间 |
| `错误：找不到被更正的节点：<id>` | `correct --target` 指错 | 核对 id |
| `错误：找不到节点：<id>` | `links --id` 指错 | 核对 id（也可能已被 `purge`） |
| `错误：找不到旧库：<path>` | `import` 的路径不对（给的是数据根但里面没有 `index.sqlite`） | 给旧库数据根，或直接给 `index.sqlite` |
| `错误：旧库不可用：不是 v1 旧库：缺少 nodes 表（<path>）` | 给了一个普通 SQLite 文件 | 确认那是 v1 的数据根 |
| `错误：--limit 必须 ≥ 1` | 试跑时给了 0 或负数 | 换成正整数 |
| `未知参数：<name>（可用：…）` | 协议调用带了命令不认识的参数 | 按提示里的可用参数改；**内核不静默丢弃** |
| `未知命令：<name>`（@@kind=not_found@@） | 协议 @@call@@ 写了不存在的命令 | 先 @@capabilities@@ 拿命令清单 |
| `协议不兼容：服务端 mmp/1，客户端 …` | @@hello@@ 的协议大版本不匹配 | 降级客户端或升级内核 |
| `不认识的 op：<op>（支持：…）` | serve 请求的 @@op@@ 拼错 | 用 §接口规范 里的 7 个 op |

### 2.3 删除与回收站

| 消息（节选） | 场景 | 怎么办 |
|---|---|---|
| `错误：没有可软删的节点：已在回收站 1 条，缺失 0 条` | 对已软删的 id 再 `forget` | 已在回收站，不用再删 |
| `错误：回收站里没有这些 id（未删除 1 条，缺失 0 条）` | `restore` 一个还活着的 id | 活数据不用恢复 |
| `错误：这些记忆还没软删，不能直接真删（先 forget）：<ids>` | 对活数据 `purge` | 先 `forget`，再 `purge --yes` |

### 2.4 运行期

| 消息（节选） | 场景 | 怎么办 |
|---|---|---|
| `错误：数据根被其他进程占用（锁：<数据根>/.mingmem-lock）；如确认无进程在写，删除该目录后重试` | 10 秒内没抢到写锁 | 等一会儿重试；确认没进程在写就删 *.mingmem-lock* 目录 |
| `错误：投影数据库错误：<...>；可执行 rebuild 重建` | `index.sqlite` 损坏 | `mingmem rebuild` |
| `错误：已中断` | Ctrl+C | 重跑；事件流只追加，不会留下半条 |
| `警告：--limit 999 超过上限 50，已按 50 执行` | `--limit` 越界 | 上限 `MAX_LIMIT = 50`，按 50 走 |
| `警告：--limit 0 无效，已按 5 执行` | `--limit` ≤ 0 | 回退默认 5 |
| `警告：命令 <cmd> 暂不支持 --json，输出为文本` | 给不支持 `--json` 的命令加了这个参数 | 忽略，或改看文本输出 |
| `警告：存在无法解析的事件行（rebuild 会跳过它们，请人工排查）` | 事件文件里有坏行 | 见 S4 |
| `缺失事件：<id> ｜ <文件>:<行号>` | `doctor` 对账不一致 | 见 S3 |
| `向量通道暂不启用：当前节点 N < 2300（计划 2300+ 后再引入）；如确需测试，设 MEM_VECTOR_FORCE=1。` | 主动要求 `--vector` 但数据太少 | 不用管；要测向量链路就设环境变量 |
| `错误：serve 目前只支持 --stdio（JSON Lines）` | 调 `serve` 没带 `--stdio` | 加 `--stdio`；没有 HTTP 模式，也不打算做 |
| 响应 `{"ok":false,"code":2,"err":"usage: …"}` | serve 请求里的 `args` 拼错了（缺参数/非法枚举） | 按响应里的 usage 改请求；这等于 CLI 的 argparse 失败 |
| 响应 `{"ok":false,"code":2,"err":"请求要带 args…"}` | 请求既没有 `args`，也不是 `op=ping/exit` | 补 `args`（字符串数组）或改用 `op` |
| 响应 `{"ok":false,"code":2,"err":"请求不是合法 JSON"}` | 一行里塞了多行 JSON / 手工拼错 | 一行一个请求 |

## 3. 故障场景

### S1 所有命令都报「未配置数据根」

不是 bug，是 D-02 的有意设计（宁可停住也不把记忆写到代码旁边）。

```
mingmem init --data-root <目录> [--default-ns project:<名>]
```

想知道配置文件在哪：看报错最后一行的「配置文件位置」，或设 `MINGMEM_CONFIG` 指到自定义位置。

**`serve` 的例外**：它在启动时解析一次数据根，之后把**这个**数据根传给每条请求（请求里带 `data_root` 可覆盖）。
所以用 `--data-root` 临时起的 serve，内部请求不会因为「配置里没写」而报未配置。

### S2 配置文件在，但数据根目录不见了（移动硬盘没插 / 拷错路径）

所有命令会用旧的绝对路径建目录 —— 如果那个盘还在，就会**在那个路径下新建一个空库**，看起来像「记忆全丢了」。
先确认路径真实存在再跑命令：

- 检查：`mingmem status` 的第一行「数据根」；
- 修正：`mingmem init --data-root <新路径> --force`；
- 数据在旧路径时，把整个数据根**拷过去**再 `doctor`。

### S3 投影与事件流不一致

`doctor` 打印 `缺失事件：<id> ｜ <文件>:<行号>` 并退出码 1，含义是「事件流里有这条，投影里没有」。

```
mingmem rebuild      # 从事件流全量重放，投影立刻恢复
mingmem doctor       # 应回到「一致」
```

投影是派生视图，**重建永远安全**（事件流不会被它改动）。

### S4 事件文件里有坏行

`status` 报 `坏行 1`，`doctor` 报「警告：存在无法解析的事件行」并退出码 1。
`rebuild` 会跳过坏行继续（`重放事件 21 条（坏行 1）`），所以系统不会卡死，但**那一条记忆等于不存在**。

处理顺序：

1. 先备份整个 `events/` 目录；
2. 定位：`doctor` 只给行数，具体位置要自己按行检查（坏行一定不是合法 JSON）；
3. 常见原因：磁盘写满、手工编辑、非 UTF-8 编码粘贴、用文本编辑器「保存为」时改了换行；
4. 能修就修成合法 JSON，修不了就删掉那一行，然后 `rebuild` + `doctor`。

### S5 锁目录残留 / 被占用

```
错误：数据根被其他进程占用（锁：<数据根>/.mingmem-lock）；如确认无进程在写，删除该目录后重试
```

- 锁是 `os.mkdir` 原子创建出来的**目录**，不是文件。
- **持锁进程还在跑**：它会每隔 `LOCK_STALE/3` 刷新锁目录 mtime（心跳），所以不会被误清 —— 等它跑完即可。
- **持锁进程被杀**：心跳消失，锁目录 mtime 超过 5 秒后，下一个命令会自动清理并接管（实测 kill 后 5.0 秒可重新拿锁）。
- 只有在「确认没有任何进程在写」时才手工删 *.mingmem-lock* 目录。
- 已知边界：`selftest` 不持锁（它起子进程，父进程持锁会互锁），所以它不能与**同库**的写命令并行。

### S6 中文乱码 / UnicodeEncodeError

Windows 默认代码页不是 UTF-8。所有调用都要带 `-X utf8` 或设 `PYTHONUTF8=1`。
调用方（别的项目、看板脚本）同样要带 —— 这是最容易忘的一条。

### S7 doctor 报「FTS5：不可用」

用了不带 FTS5 的 SQLite 构建（某些系统自带的 sqlite3）。BM25 检索会直接不可用。
换官方 Python 安装包自带的 `_sqlite3` 即可。

### S8 向量通道没启用

`status` 里的 `向量：0 条（通道未启用…）` 是**正常状态**，不是故障：设计上约 2300 条以上才引入向量（用户口径「两三千条」）。
装了 `sentence-transformers` 也只会在节点数过阈值后启用；`MEM_VECTOR_FORCE=1` 仅供测试。

### S9 路径显示成另一个盘符

例如数据根实际在 `D:\_Data\...`，命令却打印 `E:\...` —— 这是因为 `Path.resolve()` 把 junction / 符号链接解析成了真实路径。
功能完全正常；两份写法指向同一个目录。要避免混淆：用**不含 junction 的路径**做数据根。

### S10 事件文件被外部改过

三层防线各自管一件事，**不要指望其中一层全包**：

| 防线 | 能发现 | 发现不了 |
|---|---|---|
| 投影签名（名称 + 字节数 + 纳秒 mtime + 末行摘要） | 「投影过期」 | 内容改动本身 |
| `doctor` 事件↔投影对账 | 「事件有、投影里漏了」 | 事件被改（重建会把改动当成事实吸收） |
| 哈希链（`prev_hash`）+ `verify` | 「事件被改 / 删 / 插」 | **末行**被改、**整条链被重算** |
| `verify --pin`（锚点在数据根之外） | 上面两种也能发现 | 锚点文件本身被一起改 |

所以「改完事件发现一切照旧」是正常的：签名发现不一致就**自动全量重建**，改动会被当成既成事实吃进投影。
要判断「被动过没有」，跑 `mingmem verify`（有断点就退出码 1）；要防「整条链被重算」，锚点必须放在数据根之外。

### S11 真删/并发期间被打断

`purge` 对每个事件文件是「临时文件 + fsync + os.replace」原子替换，**单文件不会被撕坏**；
但多文件之间**不是事务**：极端中断下可能出现「A 文件已清、B 文件还没清」。
兜底：`mingmem doctor`（对账）+ `mingmem rebuild`（重放）。若 `purge` 中途被杀，重跑一次 `purge --ids ... --yes` 即可收敛（已清的部分会被跳过）。

### S12 真删之后发现删错了

**无法恢复。** `purge` 会物理移除事件行、清掉别处的引用，只留一条 `purge` 审计事件（内含条数与 id 的 sha256 前 16 位）。
能做的只有：从你自己的备份里把 `events/*.jsonl` 恢复回来，然后 `rebuild`。
所以真删前的最后一道闸门是 `purge --dry-run` 和 `bin` 复核 —— 见操作手册 4.6。

## 4. 备份、恢复与抢救

1. **真相源只有一个**：`<数据根>/events/*.jsonl`。备份它等于备份了整个记忆库；`index.sqlite` 不用备（可重建）。
2. 备份命令示例（Windows）：
   ```
   robocopy D:\MemoryData\events E:\backup\mingmem\events /MIR
   ```
3. 恢复：把 `events/` 拷回数据根 → `mingmem doctor` → 不一致就 `mingmem rebuild` → 再 `doctor` 应「通过」。
4. 交叉核对：`status --json` 的 `events_lines` / `nodes` / `by_ns` 与备份前记录的值对比。
5. **永远不要**为了「修数据」去手工编辑 `events/*.jsonl`；要改内容用 `correct`，要删用 `forget` / `purge`。

## 附录 A 事件类型（15 种）

| `kind` | 谁产生 | 进节点表 | 关键字段 |
|---|---|---|---|
| `episode` | `add` | ✅ | text / tags / entities / refs |
| `note` | `add` | ✅ | 同上 |
| `feel` | `add` | ✅ | 同上（E 默认 0.7） |
| `prefer` | `add` | ✅ | 同上 |
| `decide` | `add` | ✅ | 同上 |
| `consolidate` | `consolidate` | ✅（节点 kind = `node_kind`） | `node_kind` / refs=来源 / source=ai |
| `correction` | `correct` | ✅（kind=`correction`） | refs=[被更正 id]；同时把被更正者置 `superseded` |
| `access` | `recall` | ❌ | targets=[命中 id] → 强化 storage/retrieval、加共检索边 |
| `sweep` | `cycle` | ❌ | `decay`（默认 0.95）、`archived`=[转入归档的 id] |
| `archive` | 内核 | ❌ | targets |
| `link` | 内核（显式建边 / 旧库迁移） | ❌ | src / refs；可选 `edge_kind` + `weight`（绝对赋值）→ 边 |
| `consent` | `recall --include-ask` / `search --include-ask` | ❌（审计） | query / reason / targets |
| `forget` | `forget` | ❌（改标记） | targets → `erased=1, erased_at` |
| `restore` | `restore` | ❌（改标记） | targets → `erased=0` |
| `purge` | `purge --yes` | ❌（审计） | `purged_count` / `purged_sha256`（**不含 id**） |

迁移专用可选字段：`strength`（`storage/retrieval/last_access/archived/superseded/consolidated`，只由 `import` 写）、`edge_kind`/`weight`（边事件用）、`imported_from`（来源标记）。

每条事件还有 `prev_hash`（上一条事件原始字节的 sha256；首条为 `GENESIS` 或历史行前缀摘要），它是**唯一不参与业务语义、只服务于校验**的字段。

**事件重放顺序**按 `ts` 的**绝对时刻**排序（见 `text.event_sort_key`），不是按文件/行号 —— 所以跨时区写入的时间线仍然正确（自检项「G26」）。

## 附录 B 节点字段（`nodes` 表 26 列）

| 字段 | 含义 |
|---|---|
| `id` / `ns` / `kind` / `text` / `ts` | 身份与原文 |
| `S D E C I` | 六变量初值：意义 / 细节 / 情绪 / 后果 / 重要性 |
| `storage` / `retrieval` | 强度：存储强度（每次访问 `+0.05×(1-storage)`）/ 提取强度（每次 `cycle` 扫描 `×0.95`，被访问回到 1.0） |
| `last_access` | 最后一次被召回/访问的时刻 |
| `disclosure` | `public / ask / private` |
| `source` | `user / ai / mixed` |
| `tags` / `entities` / `refs` | JSON 数组字符串 |
| `consolidated` | 是否已被巩固成语义卡 |
| `archived` | 是否已归档（`storage<0.1` 且 `retrieval<0.05` 时转归档，默认不检索） |
| `superseded` / `superseded_at` | 双时态：是否被更正、何时 |
| `valid_from` / `valid_to` | 双时态：生效区间（被更正者 `valid_to` 封口） |
| `erased` / `erased_at` | 回收站：软删标记与时刻 |

配套表：`edges(src,dst,kind,weight,updated)`、`nodes_fts(id,body)`（FTS5，`unicode61` 分词器 + 我们自己在入索引时切好的 token）、`vectors(id,dim,vec)`、`meta(key,value)`。

## 附录 E 命名与文件布局

```
<数据根>/
├── events/
│   ├── project-demo.jsonl        # 一个命名空间一个文件（只追加）
│   └── global.jsonl
├── index.sqlite(+ -wal / -shm)   # 投影，可删可重建
├── .mingmem-lock/                # 运行期锁目录（正常时不存在）
└── memory.md                     # export 的默认输出
```

- **id**：`<kind 前 4 字>-<yymmddHHMMSS>-<4 位十六进制>`，例 `epis-261026231323-3e3a`。
- **命名空间文件名**：`:` 换成 `-`，其它非「字母/数字/下划线/连字符/汉字」替换成 `-`，连续 `-` 折叠；不同 ns 落到同一文件名时自动加 8 位 sha1 后缀避免混写。
- **配置文件**：Windows `%APPDATA%\mingmem\config.json`；POSIX `$XDG_CONFIG_HOME/mingmem/config.json` 或 `~/.config/mingmem/config.json`；可用 `MINGMEM_CONFIG` 覆盖。

## 附录 F schema 版本历史

| 版本 | 变更 | 旧投影 |
|---|---|---|
| 1 | 初版投影（nodes / edges / nodes_fts） | — |
| 2 | 双时态字段（`superseded / superseded_at / valid_from / valid_to`） | 自动重建 |
| 3 | 索引侧增加中文单字 token（单字查询可命中） | 自动重建 |

| 5 | 幂等键列（`client_key` + 索引，供 @@add --client-key@@） | 自动重建 |

升级代码后**不需要手动迁移**：版本号写进 `meta`，对不上就整库重放事件流。

哈希链（`prev_hash`）**不是 schema 变更**：它只加在事件行上，投影见不到它，所以没有升版本；
老数据（无 `prev_hash`）照样可读可重建，`verify` 会把它们算作「未入链」，升级后的第一次写入起自动开始串链。

## 附录 G 已知限制（诚实清单）

1. **没有真正的中文分词**：查询侧用 bigram，索引侧额外存 unigram。因此「忆内」这种不是词的两字组合仍会命中「记忆内核」（假阳性）；「内核记忆」这类换序也不会被合并。要彻底解决需要词表或分词器。
2. **没有最低相关分阈值**：一个常见词（如「数据」）的单 token 命中就能把弱相关条目带进 top5。计划与分词一起做。
3. **返回条数可能少于 `--limit`**：MMR + 硬簇上限（同簇 ≤2 条）宁可少给；负向用例可能返回 0 条。**调用方不要假设一定有 5 条**。
4. **短查询的现状段兜底会带无关结论**：③ 现状段在无重叠命中时回退到「最近 2 条结论」，可能与本条查询无关。
5. **哈希链有两条盲区**：①**末行**被改抓不到（没有后继行引用它）；②**整条链被重算**抓不到（本地校验的固有边界）。前者与后者都要靠 `verify --pin` 的外部锚点。另外链只覆盖「入链之后」的事件，更早的历史行靠首条入链事件的前缀锚点间接覆盖。
6. **真删跨文件不是事务**：单文件原子替换，多文件之间极端中断会出现部分已清（用 doctor + rebuild 收敛，见 S11）。
7. **向量通道默认不启用**（<2300 条），且需要第三方依赖；未装时降级为 BM25 + 图扩散。
8. **锁的心跳依赖进程存活**：整机休眠/进程被挂起时心跳会停，别的进程可能把锁判成残留（风险窗口 = 判定的 5 秒），这是取舍不是缺陷。
9. **路径显示可能是 junction 解析后的真实路径**（见 S9），不影响功能，但看日志时要留意。
10. **`recency` 用墙钟时间**：同日内重复跑结果字节一致（已验）；**跨天/跨月的长期衰减未做长周期验证**（未核）。
11. **`eval --gate` 的破坏性验证只覆盖 `leak_count` 越线**，`recall/mrr/redundancy` 的越线分支未各自构造破坏用例（未核）。
12. **v1 迁移的边界**：v1 没有 `valid_from/valid_to`，「双时态区间」从导入时刻起算（但 `superseded` 状态、强度、归档标记是保真的）；v1 的 `vectors` 表不迁移（向量通道本来就未启用）。
13. **`pip install -e .` 这条接入路径本会话未实测**（推荐用 `PYTHONPATH` 接法）；`pyproject.toml` 已补齐 `[build-system]` 与包发现声明，降低不确定性，但**没有真装过**（未核）。
