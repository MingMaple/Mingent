# mingmem 离线评测集

运行（仓根）：`python -X utf8 -m mingmem.eval [--gate] [--verbose] [--save-baseline]`

## 文件构成（0.2.4 起）

| 文件 | 内容 | 是否可变 |
|---|---|---|
| `seed_core.jsonl` | **原始 50 条**固定 id 事件（global / project:A / project:B，中英混排，含近重复、superseded、ask、private、跨时区、consolidate、噪声） | **冻结**：只读，扩容不碰它 |
| `seed.jsonl` | 实际载入语料 = core 50 + 扩容 186 = **236 条**（新增 project:C/D/E/F 四领域、隐私/ask 节点、跨命名空间同题、8 组近重复簇、60 条干扰项） | 由生成脚本产出 |
| `cases.jsonl` | **原始 30 条**用例（20 正向 + 6 负向 + 4 冗余敏感） | **冻结**：历史回归基准 |
| `cases_ext.jsonl` | **扩容 129 条**，带 `cat` 字段分 9 桶 | 由生成脚本产出 |
| `baseline.json` | 门禁基线（按当前评测集实测生成） | 只在有意改动后 `--save-baseline` |
| `report.json` | 每次运行的完整明细（逐用例 top5/命中/泄漏/分桶） | 覆盖写 |

生成脚本（不在核心里，属实验工具）：`_Temp/记忆内核/Scratch/gen_evalset.py`
（`--check` 只校验不写；确定性、无随机；引用 id 与 gold/must_not 冲突都会在生成时断言）。

## 用例分桶（`cat`）

| cat | 条数 | 考什么 | 期望 |
|---|---|---|---|
| `core` | 30 | 历史核心集（原样保留） | 应不低于扩容前的表现 |
| `direct` | 34 | 直问，查询与正文有明确词面重合 | 接近满分 |
| `alias` | 21 | **同义改写**（几乎不共享 bigram） | **量化"无稠密通道"的代价**，当前 0.381 |
| `short` | 13 | 1~2 字短查询 | 应命中（G17 修复后能过） |
| `multi` | 15 | 一次问两件事（gold 两条） | 看 `gold_all_rate` |
| `time` | 6 | 带月份限定的问法 | 应命中 |
| `negative` | 14 | 语料里**没有答案** | 应少给/0 条（看 `neg_avg_hits`） |
| `privacy` | 10 | private / ask 节点被直接问 | **必须 0 泄漏** |
| `namespace` | 8 | 同题不同项目（4 对，正反问） | 不得串味 |
| `redundancy` | 8 | 5 条同义复述成簇 | top5 不得被同簇占满 |

## 指标（top5）

- `recall@5`：gold 非空用例中 top5 命中**任一** gold 的比例
- `mrr@5`：首条 gold 倒数排名均值（未进 top5 记 0）
- `gold_all_rate`：**gold 全部**进 top5 的占比（`multi` 这类多目标用例的硬指标）
- `redundancy@5`：返回 ≥3 条的用例里，top5 内同簇（字符 2-gram Jaccard ≥0.6 连通）≥3 条的比例；2 条近重复是可接受预算
- `leak_count`：`must_not` 出现总次数（**必须 0**；只用于 privacy / namespace / core 的硬约束）
- `neg_avg_hits` / `neg_empty_rate`：负向用例的平均返回条数 / 返回 0 条的占比。
  **负向用例不设 `must_not`**：词面相近的条目出现是合理的（它确实是最像的东西），正确行为是"少给"
- `section_fill` / `current_rate`：六段 briefing 平均非空段数 ÷6、③ 现状段非空占比
- `avg_hits`：每例平均返回条数
- **分桶表**：每个 `cat` 的 recall/mrr/leak（诊断用，**门禁只看总体**）

## 门禁（`--gate`）

`leak_count == 0`；`recall@5 >= 基线-0.05`；`mrr@5 >= 基线-0.05`；`redundancy@5 <= 基线+0.05`；越线退出 1。

## 0.2.4 扩容：为什么指标看起来"变差"了

评测集从 **30 条 / 50 节点** 扩到 **159 条 / 236 节点**，测量对象变了，数字不可与旧值直接比：

| 指标 | 0.2.3（30 条） | 0.2.4（159 条） | 说明 |
|---|---|---|---|
| recall@5 | 1.0 | **0.8992** | 差值几乎全部来自 `alias` 桶（0.381）——同义改写没有词面重合，BM25 无能为力 |
| mrr@5 | 0.9167 | **0.8585** | 同上；且干扰项从 ~50 条涨到 236 条 |
| gold_all_rate | —（无此指标） | **0.8527** | 新增：多目标用例里两条都进 top5 的比例 |
| redundancy@5 | 0.0 | **0.0** | 近重复簇扩到 8 组（每组 5 条）仍然 0，MMR + 硬簇上限有效 |
| leak_count | 0 | **0** | privacy 10 条 + namespace 8 条 + core 的 must_not 全部 0 泄漏 |
| neg_avg_hits | —（无此指标） | **0.9** | 14 条"库里没有答案"的查询平均只返回 0.9 条 |
| neg_empty_rate | — | **0.4667** | 其中 46.7% 返回 0 条 |

**`core` 30 条在语料翻了近 5 倍之后仍是 recall 1.0 / mrr 0.9167** —— 说明原基线不是靠小语料刷出来的。

基线更新顺序（留痕，防止"用基线绕门禁"）：

1. 用旧基线跑 `--gate` → **rc=1，recall@5 越线（1.0 → 0.8992）**；
2. 确认越线原因 = 评测集规模/难度变化而不是引擎退化（逐桶看：direct 1.0、core 1.0、multi 1.0，
   只有 alias 塌陷，符合"没有稠密通道"的预期）；
3. 才 `--save-baseline` 按新集重derive；
4. 再跑 `--gate` → rc=0。

**下次谁想"提分"，先看 `alias` 桶**：那一桶是唯一真正吃能力的（0.381）。要提升只有两条路 ——
补稠密/语义通道，或者让调用方在写入时补同义词（后者属调用方职责）。
